01

環境変数はビルド時に「置換」される

process は Node.js が提供するグローバルオブジェクトであり、 ブラウザの実行環境には存在しない。DevTools のコンソールで process と打つと ReferenceError になる。

それにもかかわらずクライアントコンポーネントで process.env.NEXT_PUBLIC_〇〇 が動くのは、 Next.js のバンドラがビルド時にその文字列を値そのものへ置き換えているから。 実行時に値を読みに行っているのではなく、ソースコードを書き換えている。

ビルド前 / ビルド後

// 自分が書くコード
apiKey: process.env.NEXT_PUBLIC_FIREBASE_API_KEY

// ブラウザに配信される .js の中身
apiKey: "AIzaSyABCDEFG..."
誤解と訂正
ブラウザがビルド時に、プレフィックスの付いたものを置換対象として定める
置換するのは Next.js のバンドラ。ブラウザはビルドに一切関与せず、置換済みの .js を受け取って実行するだけ。ブラウザは NEXT_PUBLIC_ というプレフィックスの存在すら知らない

「誰が・いつ・何をするか」がズレると、サーバーコンポーネントの話で必ず混乱する。

「置換」であることから導かれる帰結

  • 値はビルド時に凍結される。Vercel で環境変数を変えても、再デプロイしなければ反映されない。ローカルでも .env.local を編集したら開発サーバーの再起動が必要
  • 動的なアクセスは置換されない。置換はテキストのパターンマッチなので、process.env[key] のように変数経由で書くと Next.js は気づけない。process.env.XXX はベタ書きが鉄則
  • ビルド時に確定するからこそ最適化できる。React は内部で process.env.NODE_ENV !== 'production' と書いており、置換後にこの条件が常に false と判明するため、開発用の警告コードごとバンドルから削除される（デッドコード削除）
  • だから絶対に隠せない。「頑張れば見える」ではなく、配信される .js に平文で書いてある
自分の目で確認すること

lib/firebase.ts を書き終えたら必ず実行し、ビルド成果物に apiKey が平文で入っていることを目視する。同時に、NEXT_PUBLIC_ の付いていない変数は grep しても出てこないことも確認する。

npm run build
grep -r "AIzaSy..." .next/static/
02

NEXT_PUBLIC_ は安全装置ではなく、公開スイッチである

誤解と訂正
NEXT_PUBLIC_ を付けることで、公開用の apiKey にもセキュリティ対策を施せる
逆。NEXT_PUBLIC_ は「この値をクライアント用バンドルに埋め込め」という指示であり、守る仕組みではなく公開する仕組み
  • 付ける ＝ 公開される
  • 付けない ＝ サーバー側にしか存在せず、ブラウザからは undefined

正しい理由づけの順序

「付けても安全だから付ける」ではない。 「付けなければ動かない。そして付けても安全である」という順序で説明する。

このアプリは Google 認証とログイン状態の購読をブラウザで行うため、Firebase の初期化コードもブラウザで動く。 NEXT_PUBLIC_ を付けなければ設定値はバンドルに埋め込まれず、ブラウザ側で undefined になってアプリが動かない。 その結果として値は公開されるが、apiKey は認可の権限を持たない公開前提の識別子なので問題にならない。

面接で説明できるようにする

NEXT_PUBLIC_ は「印」であると同時に「スイッチ」である。 実際に動作を変える機能であり、かつ、その名前を選んだ時点で開発者が「これは公開されてよい」と判断したことの表明でもある。 どちらか一方に振り切ると、公開に伴う責任の側面が抜け落ちる。

03

Firebase の apiKey と AI の APIキーは、性質がまったく違う

名前が同じ「APIキー」でも、持っていることが何を意味するかが根本的に異なる。 この違いを理由から説明できることが重要。

Firebase の apiKey 外部 AI の APIキー
正体 どのプロジェクト宛かを示す公開前提の識別子 課金権限そのものを表す秘密の資格情報
認可の権限 持たない 持つ
漏れたら データは読めない（ルールが拒否する） 不正利用され、高額請求に直結する
命名 NEXT_PUBLIC_FIREBASE_API_KEY ANTHROPIC_API_KEY（プレフィックス無し）
使う場所 ブラウザ Route Handler（サーバー側）経由のみ
仕組みとして事故が防がれている

プレフィックスを付けずに命名しておけば、うっかりクライアントコンポーネントに書いてしまっても ブラウザには届かない。付け忘れたときに起きるのは「動かない」であって「漏れる」ではない。 9-1 章の AI 機能を実装する際は、この原則を必ず守る。

04

データを守っているのはセキュリティルールだけである

誤解と訂正
コンソールで設定すれば、悪用に対して対策を取ることが「できる」
表現が弱すぎる。Firestore のセキュリティルールは、データを守っている唯一の認可の境界線。やってもやらなくてもよい追加オプションではない

apiKey が公開されていて誰でもリクエストを投げられる以上、ルール以外に守っているものは何一つない。 クライアント側のコードで if (user.uid === ...) と書いても、攻撃者はそのコードを実行しないので防御にならない。

「ルールを書けば安全になる」ではなく、「ルールを書かなければデータは丸裸である」と理解する。順序が逆。

Firestore を「本番環境モード」で作成した理由

テストモードを選ぶと「30日間、誰でも全データを読み書きできる」ルールが自動で入る。動くので気持ちがいいが、 仕様書5章の原則「デフォルトで拒否し、必要なものだけを明示的に許可する」の真逆になる。 本番環境モードなら初期状態は全アクセス拒否＝安全であり、同時に「アプリが動かない」状態でもある。 ここから firestore.rules を書いて必要な分だけ開けていく。

補足：apiKey が公開でも「何をされても平気」ではない

誰でもプロジェクトにサインアップリクエストを投げられるため、アカウントの大量作成のような悪用は原理的に可能。 それを防ぐのが Firebase App Check という仕組み（v1 では対象外）。 「ルールがあるから安全」で思考を止めないこと。

05

環境変数の命名は UPPER_SNAKE_CASE で統一する

誤解と訂正
NEXT_PUBLIC_FIREBASE_apiKey / auth_Domain / messaging _SenderId
6行の中にキャメル・スネーク・混在の3種類が混ざっていた。さらにスペースが混入しており、これは読みにくいのではなく単純に読み込みに失敗する
NEXT_PUBLIC_FIREBASE_API_KEY
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN
NEXT_PUBLIC_FIREBASE_PROJECT_ID
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID
NEXT_PUBLIC_FIREBASE_APP_ID
  • 環境変数は OS・シェルの世界の値であり、UPPER_SNAKE_CASE が universal な慣習
  • バラバラな命名はそれ自体がバグの温床になる（参照するたびに正しい綴りを思い出せない）
  • Vercel の管理画面にも同じ名前で登録するので、揺れると環境間の不一致という最もデバッグしづらい不具合を招く

書式の注意

  • = の前後にスペースを入れない
  • 値をクォートで囲む必要はない
  • .env.local は起動時にしか読まれないので、変更したら開発サーバーを再起動する
.gitignore の否定パターンには順序がある

.env.local はコミットされないため、リポジトリを clone した人には どの環境変数が必要か分からない。値を空にした .env.example をコミットするのが実務での定石。 ただし .gitignore の .env* 指定は .env.example まで無視してしまうので、 否定パターン（!）で例外を作る。 

.env*
!.env.example

この順序でなければ効かない。git は後に書かれたルールが勝つため、 !.env.example を先に書くと直後の .env* に打ち消される。

確認は目視だけでなく git check-ignore -v で機械的に行える。

$ git check-ignore -v .env.local .env.example
.gitignore:34:.env*         .env.local     ← 除外されている
.gitignore:35:!.env.example .env.example   ← 否定ルールに一致
誤解と訂正
.env.example に変数名だけを並べた（= が無い）
.env の書式は KEY=VALUE であり、= の無い行は定義として成立しない。変数名の「一覧」ではなく、そのままコピーして使える「テンプレート」であることが本質

cp .env.example .env.local して値を埋めるだけ、という状態が正解。 ダミー値は入れない——本物か偽物かで迷いが生じるうえ、空なら「未設定」であることが一目で分かる。 先頭に # コメントで値の取得元を書いておくと、テンプレートとして完成する。

06

なぜ window ではなく process.env を置換するのか

技術的には window を使う方式も可能で、実際に存在する。 サーバーが HTML を生成する際に <script>window.__ENV__ = {...}</script> を埋め込む古典的な手法があり、 Next.js のドキュメントも、ビルド後に値を変えたい場合は自前で API を用意せよと書いている。 process.env 方式が唯一の道ではない。それでも標準に選ばれた理由は4つ。

① サーバーとクライアントで同じ書き方ができる（最大の理由）

Next.js の本質は、サーバーで動くコードとブラウザで動くコードが 同じ言語・同じファイルツリー・同じ import 文で書かれること。 もし読み方を書き分ける仕様だったら、コンポーネントをサーバー↔クライアント間で移動させるたびに書き換えが必要になる。 Next.js ではこの移動が日常的に起きるため、相当な負債になる。

② エコシステムがそれを前提に作られている

process.env から設定を読むのは Node.js 文化における20年来の業界標準。 象徴的な例が React 自身で、ブラウザで動くライブラリでありながら内部で process.env.NODE_ENV を参照している。 ブラウザ向けバンドルで process.env を置換する仕組みは Next.js の発明ではなく、webpack の時代からの既定路線。 （Vite は import.meta.env という別方式を使っており、「process.env でなければならない」わけではないことの証拠になる。）

③ ビルド時に確定するからこそ最適化ができる

window.__ENV__ だと値は実行時にしか分からないため、React の開発用警告コードを削除できず、バンドルサイズが無駄に膨らむ。 「ビルド時に確定する」という制約は、不便さと引き換えに最適化を可能にしている。

④ デフォルトが安全側に倒れる

デフォルトでは環境変数はサーバー専用で、公開したければ NEXT_PUBLIC_ を付けて明示的にオプトインする。 window.__ENV__ にまとめて流し込む方式では「うっかり全部入れてしまう」事故が起きる。

同じ設計思想が別の場所にも現れている

この「失敗が安全側に倒れる」「デフォルトで拒否し、必要なものだけ明示的に許可する」という原則は、 仕様書5章で Firestore のセキュリティルールをワイルドカードでまとめず コレクションごとに個別記述する理由とまったく同じ。 優れた設計は、同じ原則が違う場所に繰り返し現れる。

07

Firebase の初期化は「ブラウザでしか動かない」わけではない

誤解と訂正
Firebase の初期化コードは、そもそもブラウザでしか動かない
事実として誤り。Firebase の JavaScript SDK は Node.js 上でも動く。正しくは「このアプリの設計上、ブラウザで動かす必要がある」

SDK の制約ではなく、このアプリが何をしたいかから来る要請である。理由は3つ。

  1. signInWithPopup（Google 認証）はブラウザの window を開く処理であり、サーバーには window がない
  2. onAuthStateChanged によるログイン状態の購読は、ブラウザ上で継続的に動き続ける必要がある
  3. ログイン状態の永続化はブラウザの IndexedDB に保存される。サーバーには保存先がない
この区別が重要な理由

「ブラウザでしか動かない」と覚えると、「Firebase を使う以上すべてクライアントコンポーネントにするしかない」 という誤った結論に飛ぶ。実際にはどこで動かすべきかは自分で設計するもの。 9-1 章の AI 機能を実装する段階では「サーバー側で Firebase を扱う」選択肢を検討することになるが、 この誤解を持っていると選択肢自体が見えなくなる。

08

IndexedDB と、認証状態が3つある理由

IndexedDB はブラウザに標準で組み込まれたクライアントサイドのデータベース。 サーバーは一切関与せず、ユーザーのPCの中だけに存在する。

容量 保存できる型 API サーバーへ送信
Cookie 4KB 程度 文字列 同期 毎リクエスト自動送信
localStorage 5MB 程度 文字列のみ 同期（メインスレッドを止める） されない
IndexedDB 数百MB〜 オブジェクト・配列・Blob 非同期 されない

Firebase Auth はログイン時に受け取ったID トークンとリフレッシュトークンをここに保存する。 だからページをリロードしてもログイン状態が消えない。 localStorage ではなく IndexedDB なのは、内部状態をオブジェクトのまま保存でき、非同期で UI をブロックしないため。

実装時に必ず効いてくる：認証状態は3つある

IndexedDB は非同期。つまりページを開いた瞬間、Firebase はまだユーザーがログイン済みか知らない。 トークンを読み出して有効性を確認するまでの数十〜数百ミリ秒、状態は「不明」である。 そのため onAuthStateChanged は最初に必ず null を返しうる。 これを「未ログイン」と解釈すると、リロードのたびに一瞬ログイン画面が表示されてから切り替わるという素人臭い挙動になる。

  1. 確認中（IndexedDB を読んでいる）→ ローディング表示
  2. 未ログイン（確認した結果いなかった）→ ログイン画面
  3. ログイン済み → アプリ本体

仕様書6章で Context に user だけでなくローディング状態を持たせると書いたのは、これが理由。 2状態で作ると必ずバグる。

面接で刺さる論点：トークンの置き場所

IndexedDB は JavaScript から自由に読めるため、XSS を許すとトークンを盗まれる。 対して Cookie には HttpOnly 属性があり、これを付けると JavaScript から一切読めなくなる。 「トークンは HttpOnly Cookie に置くべきか、IndexedDB でよいか」は実務で頻繁に議論される論点であり、 Firebase は SDK の扱いやすさを優先して IndexedDB を選んでいる、というトレードオフの上に成り立っている。

09

npm install は、他人のコードを自分の権限で実行する操作でもある

package.json の scripts には、npm が特定のタイミングで自動実行する予約された名前がある。 dev や build は npm run と打たないと動かないが、 preinstall / install / postinstall は打つ必要がない。 

// node_modules/@firebase/util/package.json
"scripts": {
  "postinstall": "node ./postinstall.js"   ← npm install した瞬間に走る
}
誤解と訂正
npm install はダウンロードする処理ではない
否定ではなく追加。ダウンロードだけではない。またすべてのパッケージがスクリプトを持つわけではなく、今回は439個中3個だけだった

実行されるコードはあなたのユーザー権限で動く。つまりターミナルでできることは何でもできる—— ~/.ssh/id_rsa を読む、.env.local を読む、読んだものを任意のサーバーへ送信する。

規模の問題：4個選んで439個入る

package.json に書いた依存は next / react / react-dom / firebase の4個。 実際に入ったのは 439個。残りは依存の依存として自動的に付いてくる。

  1. どのパッケージのどのスクリプトか特定する
  2. node_modules/〇〇/ の該当ファイルを実際に開いて読む
  3. 何をするか確認する（ファイルを書くか / 通信するか / 何もしないか）
  4. 自分のアプリに必要な機能かを判断する
  5. スキップして壊れないか、実際にビルド・lint を回して確認する

  • protobufjs — バージョン表記の警告を出すだけ。ファイルも作らず通信もしない
  • unrs-resolver — ESLint 関連。npm run lint を実際に実行し、問題なく動作することを確認済み
仕様書の判断が、別の角度からも裏付けられた

依存を増やすことは、それ自体がリスクを増やす行為である。 仕様書でカレンダーUIを外部ライブラリなしで自作すると決めたこと、Vite を併用しないと決めたことは、 学習目的だけでなくこの観点からも筋が通っている。

package-lock.json は再現性と改竄検知の両方を担う

前提：Vercel は自分の node_modules を見ていない

Vercel がやるのは git リポジトリを clone してビルドすること。 node_modules の439個は .gitignore に入っており git の管理下にすらないので、 Vercel には一切送られない。リポジトリにあるファイルだけを手がかりに、439個を自力で揃え直す。

① 再現性：`^` の曖昧さを消す

"firebase": "^12.17.1" の ^ は「12.17.1 ちょうど」ではなく 「12 系なら新しくてもよい」という範囲指定。 今日は 12.17.1 でも、来月 Vercel がビルドすれば 12.30.0 が入りうる。 lock ファイルは参考情報ではなく命令書で、Vercel が判断する余地をなくす。

怖いのは「必ず壊れる」わけではないこと
  • 今日デプロイしたら動いた。来月、コードを1行も変えずにデプロイしたら壊れた
  • ローカルでは再現しない。自分の node_modules には古いバージョンが残っているから
  • 原因がコードのどこにもない。自分の変更を疑って何時間も溶かす

「何もしていないのに壊れた」——これが再現性のない環境の代償で、実務で最も嫌われる種類の不具合。

② 改竄検知：整合性ハッシュ

lock ファイルには各パッケージの integrity（sha512 ハッシュ）が記録されている。 ダウンロードしたファイルがこれと一致しなければインストールは失敗する。 バージョン番号は同じなのに中身が違う——番号だけでは同一性を保証できないので、ハッシュで中身そのものを照合する。

つまり lock ファイルをコミットしないことは、再現性と改竄検知を同時に捨てることを意味する。 エントリ 09 のサプライチェーンの話と地続きである。

③ npm install と npm ci

npm install は、package.json と lock ファイルが食い違うと lock ファイルの方を書き換えて解決してしまう。本番ビルドでそれが起きると固定した意味がない。

npm install npm ci
lock との不一致 書き換えて解決 エラーで停止
node_modules 差分更新 削除して作り直す
用途 開発中（パッケージ追加時） CI・本番ビルド

Vercel は lock ファイルを検出すると自動的にこの厳密な方式でインストールする。手で打つ必要はない。

ブランチ名とコミットは、未来の自分への索引である

誤解と訂正
git branch -c "start-up-setting" でブランチを作って移動する
git branch -c は --copy＝ブランチの複製であり、移動しない。実行後も main にいるため、そのままコミットすると main に直接入る。正しくは git switch -c chore/firebase-setup

git checkout -b でも同じことができるが、checkout は「ブランチ切り替え」と「ファイル復元」という 無関係な機能を兼ねていて紛らわしい。それを分割するために新設されたのが switch と restore なので、 今から覚えるなら switch を使う。なおブランチ名にクォートもスペースも不要・不可。

命名規約：`種別/内容`

接頭辞用途例
feat/ユーザーに見える機能追加feat/company-list
fix/バグ修正fix/date-format
chore/設定・依存・ビルドまわりchore/firebase-setup
docs/ドキュメントのみdocs/learning-log
refactor/挙動を変えない内部改善refactor/firestore-layer

ルールは小文字・ケバブケース・英語の3つ。 大文字を使わないのは、macOS と Linux でファイルシステムの大文字小文字の扱いが異なり、事故の原因になるため。 （macOS は既定で大文字小文字を区別せず、Linux は区別する。ローカルで通ったものが CI で別物として扱われる。）

却下した案 start-up-setting の問題は2つ。start-up は英語話者にはまず「スタートアップ企業」に見えること、 そして「初期設定」では範囲が広すぎて、create-next-app の話か Firebase の話か ESLint の話か判別できないこと。

1コミット ＝ 1つの目的

取り消せる単位がコミットだからである。 「学習ログの追加をなかったことにしたい」と思ったとき、全部が1コミットなら Firebase の導入ごと巻き戻る。 git revert も git bisect（バグが入ったコミットを二分探索する機能）も機能しなくなる。

コミットメッセージもブランチ名と同じ 種別: 内容 で揃える（Conventional Commits）。 内容は日本語でよいが、接頭辞は英語で統一し、途中で言語を混ぜない。

コミット前に毎回やること

git add の後、コミットする前に git status を実行し、 .env.local が「Changes to be committed」に無いことを目視する。 git add . は使わず、意図したファイルを明示的に指定する。 一度コミットすると、後から消しても git の履歴には永久に残る——秘密情報の誤コミットは取り消せない事故である。

git log もポートフォリオの一部

採用面接でリポジトリを見る人は、コードだけでなくコミット履歴も見る。 フェーズ5まで規約が一貫していれば、git log --oneline --graph そのものが 「計画的に開発した証拠」になる。

マージするとき

git merge --no-ff の --no-ff は「早送りしない」。 付けないと git はコミットを main に一直線に並べてしまい、ブランチが存在した痕跡が消える。 付けるとマージコミットが1つ作られ、git log --graph に |\ の分岐が残る—— 「この一連のコミットは1つのまとまった作業だった」という情報が履歴に保存される。

マージ済みブランチは git branch -d で削除する（-d は未マージなら拒否してくれる安全な方）。 役目を終えたブランチを残すと、半年後に「これは何だっけ」という墓場ができる。

ブランチの粒度の基準

ブランチは「マージする単位」であって「作業する単位」ではない。ソロ開発なら「一区切りついて main に戻せる状態」が単位。

  • 細かすぎ：chore/firebase-setup / chore/remove-template / docs/conventions を別々に
  • 適切：chore/project-setup にまとめて、一区切りで main へ
  • 粗すぎ：phase-1 に認証実装まで全部（動く単位で main に戻せなくなる）

ブランチ名が内容と乖離したら、push 前なら git branch -m でリネームできる。 実際 chore/firebase-setup にテンプレート掃除を載せることになったので chore/project-setup に改名した。

ターミナルで実際に詰まった点
  • vim から抜けられない — --no-ff はメッセージが必要なので git がエディタ（既定は vim）を開く。保存して終了は Esc → :wq、中止は :q!。SSH 先など VS Code が使えない環境では必ず出てくるので、この2つだけは覚える
  • dquote> が出て戻れない — 全角の ” を打つとシェルは閉じ引用符と認識せず待ち続ける。Ctrl+C で抜ける
  • ブランチ名の打ち間違い（preject）— Tab 補完を使えば存在する名前しか出ないので原理的に起きない
  • 前の行の消し残しに続けて打つ（git branch - git merge ...）— 打ち始める前に Ctrl+U で行を消す

モジュールは「1回だけ実行される」とは限らない

前提：モジュールキャッシュ

import は「そのファイルを上から下まで実行して、export されたものを受け取る」操作。 そして同じファイルを何箇所から import しても、実行されるのは最初の1回だけで、 2回目以降は最初の結果が使い回される。これをモジュールキャッシュという。

用語：モジュールグラフ / バンドラ / バンドル

用語意味
モジュールグラフどのファイルが何を import しているかの依存関係の地図
バンドラ地図を辿ってファイルを集め、変換・最適化して出力する道具（Next.js は Turbopack）
バンドルその成果物。.next/static/ に出る
バンドラは「集める」だけの道具ではない

「ファイル数を減らして速くする」は歴史的な理由で、HTTP/2 以降は弱い。本質は変換にある。

  • 解決 — ブラウザは import ... from "firebase/app" のパッケージ名を解決できない（node_modules を知らない）。バンドラが実体に繋ぎ変える
  • 変換 — ブラウザは TypeScript も JSX も読めない
  • 最適化 — tree shaking、圧縮、そして環境変数の置換

エントリ01で「置換するのはブラウザではなくバンドラ」と訂正した、その「バンドラ」の正体がこれ。

「1回だけ」を壊す2つの例外

  1. Next.js はバンドルを2つ持つ。サーバー用（Node.js で HTML を作る）とクライアント用（ブラウザで動く）。 メモリを共有しないので、同じ lib/firebase.ts がそれぞれの世界で1回ずつ、計2回評価される。 モジュールキャッシュの保証はバンドルの内側でしか効かない
  2. HMR。ファイル保存時に、変更されたモジュールをキャッシュから捨てて再評価する。 「最初の1回だけ」の保証を、変更を反映するためにわざと壊している
誤解と訂正 ①
「トップレベル」＝ ファイルの一番上の行
関数の外側という意味。ファイルの100行目でも関数の外なら「トップレベル」。モジュールが読み込まれた瞬間に走る場所を指す

auth / db を他のファイルから import したいので export が必要で、 export するには関数の外に置くしかない。トップレベルに書くのは「そう書くと良いから」ではなく、そうせざるを得ないから。 その結果「読み込むたびに走る」性質が付いてくる。

Firebase 側で何が起きているか

Firebase SDK は内部に「作ったアプリの名簿」（_apps）を持つ。 名前を指定しない initializeApp(config) のアプリ名は "[DEFAULT]"。 

initializeApp(config) が呼ばれた
  └─ 名簿に "[DEFAULT]" が ある？
       ├─ ある → 設定は前回と同じ？
       │           ├─ 同じ → 【既存のものを返す】 ← return existingApp
       │           └─ 違う → 【エラー】duplicate-app
       └─ ない → 【新しく作って名簿に登録】
誤解と訂正 ②
再実行されることで設定が更新され、エラーを吐かなくなる
因果が逆。再実行はエラーを防ぐ側ではなく引き起こす側。古いアプリが名簿に残ったまま新しい設定で作ろうとして衝突する

名簿は lib/firebase.ts ではなく node_modules/@firebase/app の中にある。 HMR が捨てるのは変更したモジュールだけなので、名簿は生き残る。 そして Firebase には「既存アプリの設定を差し替える」APIが存在しないので、 比較して違えばエラーを投げるしかない。「更新する」という動作はどこにも実装されていない。

ガードと冪等性

冪等とは「同じ操作を何回繰り返しても、1回だけ行ったときと結果が変わらない」性質。 エレベーターのボタンを10回押しても来るのは1台、というのと同じ。

getApps() は作成済みアプリの配列を返し、無ければ空配列（エラーにならないので安全に調べられる）。 getApp() はアプリそのものを返し、無ければエラー。 この2つを使い、2回目以降は initializeApp を呼ばせないのがガードの役目。呼ばれなければ衝突しようがない。

ガードは「エラーを防ぐ回避策」ではなく「このモジュールは冪等である」という宣言。 SDK の内部実装（return existingApp）に依存せず、自分のコードで保証する。

ガードには副作用がある
設定を変えて再評価されたとき
ガード無しduplicate-app エラー。うるさいが、異常に気づける
ガード有り古い設定のまま動き続ける。静かだが、気づけない

「エラーが出ない＝正しく動いている」ではない。ガードは問題を解決したというより、見えなくした側面もある。 だから環境変数を変えたら開発サーバーを再起動するという運用とセットで初めて成立する。 エントリ01の「.env.local を変更したら再起動が必要」と同じ話。

"use client" は境界の宣言であって「ブラウザ専用」ではない

前作の React だけのアプリでは、コードが動く場所はブラウザの1箇所だけだった。 Next.js ではサーバー（Node.js）とブラウザの2箇所で動く。 「このコードはどっちで動くのか」を意識する必要が生まれた——これが React 単体との最大の違い。

サーバーコンポーネントクライアントコンポーネント
書き方何も書かない（既定）ファイル先頭に "use client"
JSがブラウザへ送られない送られる
useState / onClick使えない使える
useEffect使えない使える
誤解と訂正
"use client" ＝「これはブラウザでだけ動く」
「これはサーバーで動き、加えてブラウザにも送られてもう一度動く」。クライアントコンポーネントは計2回実行される

Next.js のドキュメントは boundary（境界） と entry point（入口） という語を使っている。 「client only」ではない。名前が誤解を招く。

実行の流れ（時系列）

  1. 【第1幕】サーバーで HTML を作る — サーバーコンポーネントもクライアントコンポーネントも実行される。 ただしこの時点で window / document / IndexedDB は存在せず、 useEffect は実行されない（React がサーバーでは呼ばないと決めている）
  2. 【第2幕】ブラウザが HTML を受け取る — 画面は見えるが、まだボタンは押せない。 JS のダウンロードを待たずに表示できる、というのがサーバーで HTML を作る価値
  3. 【第3幕】ブラウザで再実行される（ハイドレーション）— ここで初めて window があり、IndexedDB があり、useEffect が動く
だから何が問題になるか

lib/firebase.ts を import するのはクライアントコンポーネントであり、 そのクライアントコンポーネントは第1幕（サーバー）でも実行される。 つまり lib/firebase.ts のトップレベルはサーバーでも走る。 

// 悪い例
export const auth = getAuth(app);
onAuthStateChanged(auth, (user) => { ... });  // ← トップレベル。サーバーでも走る

サーバーには IndexedDB が無いので、ログイン状態を読みに行って失敗する。

ルール：トップレベルには「Node.js でも壊れないもの」だけ。ブラウザ専用の処理は useEffect の中へ。 initializeApp / getAuth / getFirestore はインスタンスを作るだけなのでトップレベルで問題ない。

結果：サーバーはユーザーが誰か知りようがない

ログイン情報はブラウザの IndexedDB にあり、サーバーは別のマシンなので見られない。 したがってサーバーが作る HTML は、必ず「まだ誰か分からない」状態のものになる。 第3幕で useEffect が動いて初めて「ログイン済みだった」と判明する。

エントリ08の「状態は3つ必要」が、ここでも別の角度から裏付けられた。 ①を用意せず「user が null なら未ログイン」と書くと、 サーバーが作る HTML は必ずログイン画面になり、リロードのたびに一瞬ちらつく。

境界は1箇所に引く

app/layout.tsx              ← サーバーコンポーネント（何も書かない）
  └─ AuthProvider.tsx       ← "use client" ★ 境界はここ
       └─ lib/firebase.ts   ← 自動的にクライアントバンドルに含まれる

★ の1行を書けば、そこから import されるものは Next.js が依存関係を辿って自動でクライアント側に含める。 lib/firebase.ts はコンポーネントですらない（JSX も state も持たない、値を export するだけのファイル）ので、 境界を宣言する立場にない。"use client" は不要。

ドキュメントも明言している：You do not need to add the 'use client' directive to every file that contains Client Components.

Next.js には2つのルーティング方式があり、App Router が新しい方（Next.js 13 で導入）。

ディレクトリpages/app/

フォームは「state が正、画面はその写し」

React の入力欄には value と onChange の両方を持たせる。

  • value — 「表示する値は state のこれ」

片方だけだと壊れる。value だけ書くと state が変わらないので、 何を打っても入力欄が変化しない（React が state の値を表示し続けるため）。 この「state が唯一の正しい値で、入力欄はそれを映しているだけ」という形を制御コンポーネントと呼ぶ。

  • スクリーンリーダーがラベルとして読み上げるとは限らない。あくまで補助的なヒント用の属性
  • コントラストが低く、そもそも読みにくい

<input id="email" type="email" ... />

htmlFor と id を一致させるとラベルのクリックで入力欄にフォーカスが当たる。 React で for ではなく htmlFor なのは、for が JavaScript の予約語だから （class → className と同じ理由）。エントリ15の lang="ja" と同じアクセシビリティの基本。

囲む理由ができてから囲む

() => setMode("signup")
^^    ^^^^^^^^^^^^^^^^^
①  ②        ③

① 引数のリスト（空 = 引数なし）
② 「ここから関数の中身」という区切り
③ 関数の中身

分岐と条件表示の書き分け

書き方使う場面
三項演算子 A ? B : C値が欲しいとき（式）。どちらかを必ず出す
if / else処理を分けたいとき（文）
&&あるときだけ出す（無いときは何も描画しない）
誤解と訂正 ①：処理の分岐に三項演算子を使った

戻り値を使っていないので if / else が正しい。三項演算子は「値を選ぶ」もの。後でエラー処理やログを足すときにも if なら自然に書ける（三項演算子の枝に複数の処理は書けない）

さらに {} は JSX の中でだけ意味を持つ。 普通の JavaScript の関数の中に書いた {} はただのブロックで、何の役にも立っていなかった。

誤解と訂正 ②：条件付きレンダリング
{error === !"" ? (<div></div>)}
{error && <div>{error}</div>}。!"" は true なので error === true を比較しており常に false。さらに : が無く構文エラーで、中身も空だった

&& は「左が truthy なら右を評価して返す」。空文字は falsy なので何も描画されない。 「あるときだけ出す」なら三項演算子で : null と書くより短くて意図が明確。

誤解と訂正 ③：否定と比較の優先順位

! は === より先に評価されるので (!user) === null、つまり真偽値と null の比較で常に false。if (!loading && user) でよい

!a === b という形を見たら疑う。書きたかったのはほぼ確実に a !== b。

予告：&& の 0 の罠

&& は左辺の値をそのまま返すので、左辺が 0 だと画面に 0 が表示される。 文字列なら空文字は何も描画されないので安全だが、数値のときは {count > 0 && ...} と明示的に真偽値へ変換する。 企業数やカウントを扱うフェーズ5で必ず遭遇する。

型は実行時に存在しない

TypeScript はビルド時に消える。ブラウザが受け取るのは JavaScript だけ。

// 書く TypeScript
interface Foo { a: string }
const x: Foo = { a: "hi" };

// ブラウザに届く JavaScript
const x = { a: "hi" };        // ← Foo はどこにも無い

だから x instanceof Foo は比較する相手が無く、「Foo は型のみを参照します」というエラーになる。

class は違う——TypeScript の機能ではなく JavaScript の機能なので、コンパイルしても消えない。 FirebaseError が実在するからこそ error instanceof FirebaseError という実行時のチェックが成立する。

書いている最中に間違いを防ぐinterface / type / 型注釈
実行時に値の正体を確かめるinstanceof / typeof / in

「型で守れる範囲」と「実行時にしか分からない範囲」の境界がここにある。 エントリ01の「環境変数はビルド時に置換される」と同じ問い——何がビルドを生き延びて、ブラウザに届くのか。

catch の値が unknown になる理由

catch (err) {        // ← 型は書かない。書けない。TypeScript が unknown を付ける
  setError(getAuthErrorMessage(err));
}

any は「何でも許す」、unknown は「まず確かめろ」。 JavaScript は throw に何でも渡せる（文字列でも数値でも投げられる）ので、 TypeScript は確認するまで .code すら読ませない。strict 設定がこれを有効にしている。

instanceof は2つの仕事をしている

仕事
実行時この値は本当に FirebaseError か判定する
型の上それ以降のコードで error を FirebaseError として扱えるようにする（型の絞り込み）
 
if (!(error instanceof FirebaseError)) {
  return "ログインに失敗しました";   // ← Firebase 以外はここで終わり
}
error.code                            // ← ここでは読める

弾かれる側にも意味がある。FirebaseError でない例外——自分のコードのバグ、 ブラウザやネットワーク層の例外——に「メールアドレスが正しくありません」と表示したら嘘になる。 分からないものを、分かったふりで説明しない。

戻り値の型は「自分が保証したいこと」を書く場所

getAuthErrorMessage(error: unknown): string と書いておくと、 switch の default を忘れた瞬間に 「string | undefined は string に代入できない」とコンパイルエラーになる。 書かなければ undefined が画面まで届く。

「何も無い」の表し方を1種類に揃える

キャンセル時の戻り値は null ではなく空文字にした。 error state はすでに「"" ＝ 何も表示しない」という約束で動いている （{error && <div>{error}</div>}）ので、その約束にそのまま乗れる。

null を返す設計もあり得るが、「何も無い」の表し方が "" と null の2種類に増える。 呼び出し側が毎回どちらか判断することになるので、1種類に揃える。

return ""; には必ず理由を書く

なぜ空文字なのかは、コードからは絶対に読み取れない。コメントが無いと「書き忘れ」に見える。 

case AuthErrorCodes.POPUP_CLOSED_BY_USER:
case AuthErrorCodes.EXPIRED_POPUP_REQUEST:
  // ユーザーが自分で閉じただけなので、何も表示しない

誤解と訂正：説明文を return の中に書いた
return "ユーザーが自分で閉じただけなので、何も表示しない";
この文章がそのまま画面に表示される。返すのは "" で、理由は // コメントに書く

(protected)/layout.tsx で擬似コードを JSX の中に貼ったのと同じ種類の間違い。 説明はコードの外に置く。引用符の中身は、必ずユーザーの目に触れる。

秘密を送らずに、持っていることを証明する

GitHub が2021年にパスワード認証を廃止した理由は、パスワードの根本的な弱点にある。

パスワードは「秘密そのものを相手に渡して証明する」方式。 送った先が偽サイトなら盗まれ、通信を覗かれても盗まれ、相手のサーバーが漏洩しても盗まれる。

鍵認証は、秘密を一度も送らない。

あなた                                GitHub
  │  ── 接続。私は誰それです ────→    │
  │                                     │  登録済みの公開鍵を探す
  │  ←── ランダムな文字列を送る ────    │  「これに署名してみせろ」
  │  秘密鍵で署名を作る                  │
  │  ── 署名を送る ──────────→        │
  │                                     │  公開鍵で検証
  │  ←──── 認証成功 ──────────      │

流れるのは署名だけで、しかも毎回ランダムな文字列に対する署名なので、 盗んで再利用することもできない。

ファイル扱い見分け方
id_ed25519秘密鍵。絶対に外に出さない-----BEGIN OPENSSH PRIVATE KEY----- で始まる複数行
id_ed25519.pub公開鍵。配ってよいssh-ed25519 AAAA... の1行

公開鍵から秘密鍵は計算できない——できないことがこの暗号方式の前提。 エントリ03の「Firebase の apiKey（公開前提）と AI の APIキー（秘密）」と同じ構造で、 「配ってよいもの」と「絶対に出さないもの」がペアで存在する。

混同しやすい：パスフレーズは通信を守っていない
パスフレーズは、通信の安全のためにある
秘密鍵ファイルそのものを暗号化している。守るのは「ノートPCを盗まれた」「マルウェアに ~/.ssh/ を読まれた」という状況
鍵ファイルを盗まれたらパスフレーズ無しパスフレーズ有り
結果即座に本人になりすませるファイルだけでは使えない

.env.local を .gitignore に入れるのと同じ、 「持ち出されたときにどうなるか」の防御。通信の安全とは別の層。

安全と手間のトレードオフを、仕組みで解消する

パスフレーズがあると push のたびに入力を求められる。 面倒だと、人はパスフレーズを空にしてしまう。

Host github.com
  AddKeysToAgent yes        # 使うとき自動で ssh-agent に登録
  UseKeychain yes           # パスフレーズを macOS キーチェーンから取る
  IdentityFile ~/.ssh/id_ed25519

ssh-agent は復号した秘密鍵をメモリに預かり、以降の署名を代行する常駐プログラム。 この3行があるので再起動してもパスフレーズを聞かれない。

「妥協しないと不便」という状況は、設定で解消できることが多い。 不便を理由に安全性を下げる前に、仕組みで解けないか考える。

git add はファイルを指し示す操作ではなく、その瞬間の中身をコピーしてステージに置く操作。 だから add したあとに編集したら、もう一度 add しないと反映されない。

打ち間違いは、必ずしもエラーにならない

SSH の設定中に3種類の失敗をした。どれも壊れ方が違う。

① スペース1つで、後続がまるごと止まった

touch ~/ .ssh/config && open -e ~/.ssh/config
       ↑ここにスペース

シェルはスペースで区切って2つの別々の引数として受け取る—— ~/（ホーム。存在するので無視される）と .ssh/config（いる場所からの相対パス＝存在しない）。

touch が失敗したので、&& の後ろの open は実行されなかった （&& は「左が成功したときだけ右を実行する」）。 結果、テキストエディタが開かず、貼り付けた設定がそのままターミナルへ入力された。

② 大文字の Host が、コマンドとして実行された

Host github.com not found: 5(REFUSED)     ← 1行目だけ挙動が違った
zsh: command not found: AddKeysToAgent    ← 残りは command not found

/usr/bin/host（DNS を調べるコマンド）が実行された。 macOS のファイルシステムが大文字小文字を区別しないため、Host で host が見つかった。

エントリ11で学んだ話が、実地で出た

ブランチ名を小文字に統一した理由——「macOS と Linux でファイルシステムの大文字小文字の扱いが違う」——が、 まったく別の場面で牙を剥いた。Linux なら command not found で終わっていた。 知識は、学んだのと同じ形では出てこない。

③ リモートURLの打ち間違いは、push まで分からなかった

                                          ↑ o が余分

$ git push -u origin main
ERROR: Repository not found.

git remote add は文字列を記録するだけで、その時点では通信も検証もしない。 だから間違いに気づくのはpush の瞬間。

直すのは add ではなく set-url——すでに origin があるので add は拒否される。 

git remote set-url origin git@github.com:.../job-tracker.git
git ls-remote --heads origin    # 何も出なければ成功（リポジトリが空）
対策は「気をつける」ではない
  • パスは手で打たず Tab で補完する。~/.ss まで打って Tab
  • URL は GitHub の画面からコピーして貼る。手打ちしない
  • 括弧を含むパスはクォートで囲む。git add 'app/(protected)/layout.tsx'——囲まないと zsh が no matches found を出す
  • full-width の ” を打つと dquote> から抜けられなくなる。Ctrl+C で脱出

失敗の仕方が毎回違うのは、失敗する場所が毎回違うから。 覚えるべきは個々のエラーメッセージではなく、「入力を人力に頼らない手段があるなら、そちらを使う」という方針。

非同期のエラーは、書いてあっても捕まらない

try {
  load();              // ← async 関数を await せずに呼んでいる
  setLoading(false);
} catch {
  setError("企業一覧の取得に失敗しました");
}
2つ同時に壊れていた
load() を呼ぶ         → 通信が始まる（まだ終わっていない）
setLoading(false)     → 即座に実行される ← データはまだ無い
try ブロックを抜ける   → catch の守備範囲が終わる
              …数百ミリ秒後…
Firestore が失敗       → もう誰も見ていない
  1. setLoading(false) が早すぎる。データが来る前に「読み込み完了」になる
  2. catch に届かない。エラーは画面に出ず、コンソールに「未処理の Promise」として流れるだけ

try / catch は「同期的に実行される範囲」しか守らない。 await しない非同期関数は、その範囲の外で失敗する。

エントリ27「エラーは、書かなければ握り潰される」の非同期版。 今回は書いてあるのに握り潰されている——より気づきにくい。

直し方：守りたい処理と同じ関数の中に置く

useEffect(() => {
  if (!user) return;

  const load = async () => {
    setError("");
    try {
      setCompanies(await getCompanies(user.uid));
    } catch {
      setError("企業一覧の取得に失敗しました");
    } finally {
      setLoading(false);
    }
  };

  load();
}, [user]);

finally は try でも catch でも必ず実行される。 setLoading(false) はどちらの場合も必要なので、2箇所に書かず finally に1回書く—— 片方を消し忘れる・書き忘れる事故が構造的に起きなくなる。

React のルール：useEffect に渡した関数の返り値が「関数」なら、後始末関数として保存する。 async を付けると返り値は必ず Promise になる。関数ではないので React が警告する （黙って壊れるのではなく、検知して警告する）。

だから中で別の非同期関数を定義して呼ぶ形になる。

後始末関数（クリーンアップ関数）とは

「始めたものを、終わらせる」ための関数。すでに AuthContext.tsx で書いていた。

const unsubscribe = onAuthStateChanged(auth, ...);
return unsubscribe;      // ← これが後始末関数

監視は始めたら止めないと、コンポーネントが消えた後も動き続け、消えたコンポーネントの setState を呼ぼうとする（メモリリーク）。

始める終わらせる
onAuthStateChanged(...)unsubscribe()
setInterval(...)clearInterval(...)
addEventListener(...)removeEventListener(...)

逆に getCompanies のような1回きりの取得には後始末が要らない——動き続けているものが無いから。

誤解と訂正：await は「ブラウザを止める」
データを取ってくるまで、そこで止めておく処理
止まるのはその関数の中の流れだけ。ブラウザ全体は動き続ける（ボタンも押せる、他の描画もできる）

await は「この関数はここで一旦席を外し、返事が来たら続きから再開する」という意味。 もしブラウザ全体が止まったら、通信中はページが固まって何も操作できない—— エントリ08で IndexedDB が非同期である理由として書いた「UI をブロックしない」がこれ。

どちらも頻繁に変わる。違うのは型の種類

型検査が届かない場所

キーだけを借りる — Record と keyof

  • 通信や書き込みをする → 2回起きる
  • 外の変数を書き換える → 2回加算される
  • 乱数や現在時刻を使う → 1回目と2回目で結果が違う

本番ビルドでは1回。Strict Mode の目的は「分けること」ではなく「混ざっていたら症状を出すこと」で、結果として境界が守られる。

これは例外ではなく、基準を適用した結果。「頻度が高いから」だけだと「メモも頻度が高い」に答えられない—— メモは自由入力なので中間状態があり、基準で切れる。基準は、次の判断にも使えて初めて基準。

存在しない ID は null を返し、「見つかりません」を表示する

捨てた案
getCompany が例外を投げ、error.tsx やページの error state が受け止める
理由
「見つからない」はエラーではない。URL を手で書き換えれば誰でも起こせる想定内のことで、 通信失敗やルール違反とは種類が違う。ユーザーに伝えるべき内容も違う—— 「もう一度お試しください」ではなく「この企業は存在しません」。 キャンセルをエラー扱いした件（エントリ34）と同じ形の問い。
表示を分けない
「存在しない ID」と「他人の企業の ID」で表示を変えると、 その ID が実在するかどうかを総当たりで確かめられる。
そもそも区別が生まれない
階層型を選んだ結果、「他人のID」という状態が発生しない。 getCompany(uid, id) の uid は useAuth()（本人）、id は URL—— 組み立てられるパスは常に users/自分のuid/companies/URLのid で、他人のパスを作る方法がない。 permission-denied は起きず、「存在しない ID」とまったく同じ経路を通る。
フラット型だったら
他人の文書を直接指すパスが作れてしまい permission-denied が返る。 そこで初めて「拒否されたことを隠して『見つかりません』と表示する」工夫が必要になり、書き忘れれば存在確認の穴になる。 設計で消せる仕事は、設計で消す（エントリ42）。

URL の protocol 判定を lib/validation.ts に切り出す

経緯
同じ判定が2箇所で必要になった——登録フォームの検証（エラーメッセージを返す）と、 詳細ページの表示（リンクにするかどうか）。2つ目の使用例が出た（エントリ28）。
捨てた案
(a) 詳細ページに独自に書く（登録フォームには触らない） (b) lib/firestore.ts に置く
理由
(a) は「許可するプロトコル」が2箇所になり、将来変えるとき片方を忘れる。 (b) は責務が違う——lib/firestore.ts の関数はすべて db を使い通信するが、 protocol 判定は Firestore が存在しなくても動く。 「登録するデータの検証だから関係している」は連想であって責務ではない—— その論法だと validateCompanyInput も todayString も入ってしまう。
ファイル名の基準
「そこに他に何が入るか」。lib/url.ts より lib/validation.ts の方が、 今後入るものが具体的に想像できる（validateCompanyInput も、編集ページを作るときに移す候補）。
関数名
isSafeUrl ではなく isHttpUrl。 「safe」は結論であって判定内容ではない——何に対して安全かは中を読まないと分からない。 そして「安全」の基準は使う場面で変わる（<a href> なら http: で十分だが、通信用途なら不十分）。 判定内容で名付けると、使う側が自分の用途に合うか判断できる—— getAuthErrorMessage を Firestore に流用できなかったのと同じ形（エントリ47）。
副次的な効果
validateCompanyInput から try/catch が消えた。 例外を投げうる処理が isHttpUrl の中に移ったため（エントリ51）。

保存済みの jobUrl を、表示側でも検証する

経緯
前回の未解決の問い。入力時に javascript: を弾いても、 Firebase コンソールから手で書き込まれた値はその検証を通っていない（エントリ47）。
捨てた案
入口の検証だけで足りるとみなす。書き込む口は自分のアプリとコンソールの2つだけで、被害も自分だけ
理由
「発生確率が低い」ではなく「コストの非対称性」で判断すると決めてある（エントリ21）。
払うコスト防ぐもの
href に渡す前に isHttpUrl を呼ぶ。数行自分の画面で任意のスクリプトが動く
切り出した関数がすでにあるので、コストはさらに下がっていた。
他の項目を検証しない理由
実害の大きさが桁違い。他の項目に不正な値が入っても表示が崩れるだけだが、 jobUrl は <a href> に渡るため任意コード実行につながる。 同じ「コンソールから入れられる」でも、防ぐ価値が違う。
表示の設計
3状態に分けた。空欄→「URLが登録されていません」（href="" は現在のページを指すので出さない）、 不正→「不正なURLです。編集ページでURLを入れ直してください」、正常→ <a target="_blank" rel="noopener noreferrer">。 noreferrer は noopener の効果（元ページを操作させない）に加え、参照元URLを送らない。

Firestore のオフライン時の挙動を、いまは受け入れる

問題
オフラインでは updateDoc の Promise が解決も拒否もしないため、 await の先にある finally に到達せず、 <select> が disabled のままオンライン復帰まで戻らない（エントリ62）。
捨てた案
(a) navigator.onLine で送信前に弾く (b) タイムアウトを設けて一定時間で catch に落とす (c) await をやめる（SDK が推奨する形）
理由
(c) は成功・失敗が分からなくなるので、「保存されていないのに画面に映る」を避けるという判断と衝突する。 (a)(b) は実装できるが、就活中にステータスを変える場面は、ネットワークが安定した環境であることがほとんど。 知った上で、いまは払わないと決めた。
見直す条件
「<select> が disabled のまま戻らない」状況に実際に遭遇したら。 曖昧な「問題が起きたら」ではなく症状で書いておく——後から判断できるように。
