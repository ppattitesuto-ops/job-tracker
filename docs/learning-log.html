01

環境変数はビルド時に「置換」される

process は Node.js が提供するグローバルオブジェクトであり、 ブラウザの実行環境には存在しない。DevTools のコンソールで process と打つと ReferenceError になる。

それにもかかわらずクライアントコンポーネントで process.env.NEXT_PUBLIC_〇〇 が動くのは、 Next.js のバンドラがビルド時にその文字列を値そのものへ置き換えているから。 実行時に値を読みに行っているのではなく、ソースコードを書き換えている。

ビルド前 / ビルド後

// 自分が書くコード
apiKey: process.env.NEXT_PUBLIC_FIREBASE_API_KEY

// ブラウザに配信される .js の中身
apiKey: "AIzaSyABCDEFG..."
誤解と訂正
ブラウザがビルド時に、プレフィックスの付いたものを置換対象として定める
置換するのは Next.js のバンドラ。ブラウザはビルドに一切関与せず、置換済みの .js を受け取って実行するだけ。ブラウザは NEXT_PUBLIC_ というプレフィックスの存在すら知らない

「誰が・いつ・何をするか」がズレると、サーバーコンポーネントの話で必ず混乱する。

「置換」であることから導かれる帰結

  • 値はビルド時に凍結される。Vercel で環境変数を変えても、再デプロイしなければ反映されない。ローカルでも .env.local を編集したら開発サーバーの再起動が必要
  • 動的なアクセスは置換されない。置換はテキストのパターンマッチなので、process.env[key] のように変数経由で書くと Next.js は気づけない。process.env.XXX はベタ書きが鉄則
  • ビルド時に確定するからこそ最適化できる。React は内部で process.env.NODE_ENV !== 'production' と書いており、置換後にこの条件が常に false と判明するため、開発用の警告コードごとバンドルから削除される（デッドコード削除）
  • だから絶対に隠せない。「頑張れば見える」ではなく、配信される .js に平文で書いてある
自分の目で確認すること

lib/firebase.ts を書き終えたら必ず実行し、ビルド成果物に apiKey が平文で入っていることを目視する。同時に、NEXT_PUBLIC_ の付いていない変数は grep しても出てこないことも確認する。

npm run build
grep -r "AIzaSy..." .next/static/
02

NEXT_PUBLIC_ は安全装置ではなく、公開スイッチである

誤解と訂正
NEXT_PUBLIC_ を付けることで、公開用の apiKey にもセキュリティ対策を施せる
逆。NEXT_PUBLIC_ は「この値をクライアント用バンドルに埋め込め」という指示であり、守る仕組みではなく公開する仕組み
  • 付ける ＝ 公開される
  • 付けない ＝ サーバー側にしか存在せず、ブラウザからは undefined

正しい理由づけの順序

「付けても安全だから付ける」ではない。 「付けなければ動かない。そして付けても安全である」という順序で説明する。

このアプリは Google 認証とログイン状態の購読をブラウザで行うため、Firebase の初期化コードもブラウザで動く。 NEXT_PUBLIC_ を付けなければ設定値はバンドルに埋め込まれず、ブラウザ側で undefined になってアプリが動かない。 その結果として値は公開されるが、apiKey は認可の権限を持たない公開前提の識別子なので問題にならない。

面接で説明できるようにする

NEXT_PUBLIC_ は「印」であると同時に「スイッチ」である。 実際に動作を変える機能であり、かつ、その名前を選んだ時点で開発者が「これは公開されてよい」と判断したことの表明でもある。 どちらか一方に振り切ると、公開に伴う責任の側面が抜け落ちる。

03

Firebase の apiKey と AI の APIキーは、性質がまったく違う

名前が同じ「APIキー」でも、持っていることが何を意味するかが根本的に異なる。 この違いを理由から説明できることが重要。

Firebase の apiKey 外部 AI の APIキー
正体 どのプロジェクト宛かを示す公開前提の識別子 課金権限そのものを表す秘密の資格情報
認可の権限 持たない 持つ
漏れたら データは読めない（ルールが拒否する） 不正利用され、高額請求に直結する
命名 NEXT_PUBLIC_FIREBASE_API_KEY ANTHROPIC_API_KEY（プレフィックス無し）
使う場所 ブラウザ Route Handler（サーバー側）経由のみ
仕組みとして事故が防がれている

プレフィックスを付けずに命名しておけば、うっかりクライアントコンポーネントに書いてしまっても ブラウザには届かない。付け忘れたときに起きるのは「動かない」であって「漏れる」ではない。 9-1 章の AI 機能を実装する際は、この原則を必ず守る。

04

データを守っているのはセキュリティルールだけである

誤解と訂正
コンソールで設定すれば、悪用に対して対策を取ることが「できる」
表現が弱すぎる。Firestore のセキュリティルールは、データを守っている唯一の認可の境界線。やってもやらなくてもよい追加オプションではない

apiKey が公開されていて誰でもリクエストを投げられる以上、ルール以外に守っているものは何一つない。 クライアント側のコードで if (user.uid === ...) と書いても、攻撃者はそのコードを実行しないので防御にならない。

「ルールを書けば安全になる」ではなく、「ルールを書かなければデータは丸裸である」と理解する。順序が逆。

Firestore を「本番環境モード」で作成した理由

テストモードを選ぶと「30日間、誰でも全データを読み書きできる」ルールが自動で入る。動くので気持ちがいいが、 仕様書5章の原則「デフォルトで拒否し、必要なものだけを明示的に許可する」の真逆になる。 本番環境モードなら初期状態は全アクセス拒否＝安全であり、同時に「アプリが動かない」状態でもある。 ここから firestore.rules を書いて必要な分だけ開けていく。

補足：apiKey が公開でも「何をされても平気」ではない

誰でもプロジェクトにサインアップリクエストを投げられるため、アカウントの大量作成のような悪用は原理的に可能。 それを防ぐのが Firebase App Check という仕組み（v1 では対象外）。 「ルールがあるから安全」で思考を止めないこと。

05

環境変数の命名は UPPER_SNAKE_CASE で統一する

誤解と訂正
NEXT_PUBLIC_FIREBASE_apiKey / auth_Domain / messaging _SenderId
6行の中にキャメル・スネーク・混在の3種類が混ざっていた。さらにスペースが混入しており、これは読みにくいのではなく単純に読み込みに失敗する
NEXT_PUBLIC_FIREBASE_API_KEY
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN
NEXT_PUBLIC_FIREBASE_PROJECT_ID
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID
NEXT_PUBLIC_FIREBASE_APP_ID
  • 環境変数は OS・シェルの世界の値であり、UPPER_SNAKE_CASE が universal な慣習
  • バラバラな命名はそれ自体がバグの温床になる（参照するたびに正しい綴りを思い出せない）
  • Vercel の管理画面にも同じ名前で登録するので、揺れると環境間の不一致という最もデバッグしづらい不具合を招く

書式の注意

  • = の前後にスペースを入れない
  • 値をクォートで囲む必要はない
  • .env.local は起動時にしか読まれないので、変更したら開発サーバーを再起動する
.gitignore の否定パターンには順序がある

.env.local はコミットされないため、リポジトリを clone した人には どの環境変数が必要か分からない。値を空にした .env.example をコミットするのが実務での定石。 ただし .gitignore の .env* 指定は .env.example まで無視してしまうので、 否定パターン（!）で例外を作る。 

.env*
!.env.example

この順序でなければ効かない。git は後に書かれたルールが勝つため、 !.env.example を先に書くと直後の .env* に打ち消される。

確認は目視だけでなく git check-ignore -v で機械的に行える。

$ git check-ignore -v .env.local .env.example
.gitignore:34:.env*         .env.local     ← 除外されている
.gitignore:35:!.env.example .env.example   ← 否定ルールに一致
誤解と訂正
.env.example に変数名だけを並べた（= が無い）
.env の書式は KEY=VALUE であり、= の無い行は定義として成立しない。変数名の「一覧」ではなく、そのままコピーして使える「テンプレート」であることが本質

cp .env.example .env.local して値を埋めるだけ、という状態が正解。 ダミー値は入れない——本物か偽物かで迷いが生じるうえ、空なら「未設定」であることが一目で分かる。 先頭に # コメントで値の取得元を書いておくと、テンプレートとして完成する。

06

なぜ window ではなく process.env を置換するのか

技術的には window を使う方式も可能で、実際に存在する。 サーバーが HTML を生成する際に <script>window.__ENV__ = {...}</script> を埋め込む古典的な手法があり、 Next.js のドキュメントも、ビルド後に値を変えたい場合は自前で API を用意せよと書いている。 process.env 方式が唯一の道ではない。それでも標準に選ばれた理由は4つ。

① サーバーとクライアントで同じ書き方ができる（最大の理由）

Next.js の本質は、サーバーで動くコードとブラウザで動くコードが 同じ言語・同じファイルツリー・同じ import 文で書かれること。 もし読み方を書き分ける仕様だったら、コンポーネントをサーバー↔クライアント間で移動させるたびに書き換えが必要になる。 Next.js ではこの移動が日常的に起きるため、相当な負債になる。

② エコシステムがそれを前提に作られている

process.env から設定を読むのは Node.js 文化における20年来の業界標準。 象徴的な例が React 自身で、ブラウザで動くライブラリでありながら内部で process.env.NODE_ENV を参照している。 ブラウザ向けバンドルで process.env を置換する仕組みは Next.js の発明ではなく、webpack の時代からの既定路線。 （Vite は import.meta.env という別方式を使っており、「process.env でなければならない」わけではないことの証拠になる。）

③ ビルド時に確定するからこそ最適化ができる

window.__ENV__ だと値は実行時にしか分からないため、React の開発用警告コードを削除できず、バンドルサイズが無駄に膨らむ。 「ビルド時に確定する」という制約は、不便さと引き換えに最適化を可能にしている。

④ デフォルトが安全側に倒れる

デフォルトでは環境変数はサーバー専用で、公開したければ NEXT_PUBLIC_ を付けて明示的にオプトインする。 window.__ENV__ にまとめて流し込む方式では「うっかり全部入れてしまう」事故が起きる。

同じ設計思想が別の場所にも現れている

この「失敗が安全側に倒れる」「デフォルトで拒否し、必要なものだけ明示的に許可する」という原則は、 仕様書5章で Firestore のセキュリティルールをワイルドカードでまとめず コレクションごとに個別記述する理由とまったく同じ。 優れた設計は、同じ原則が違う場所に繰り返し現れる。

07

Firebase の初期化は「ブラウザでしか動かない」わけではない

誤解と訂正
Firebase の初期化コードは、そもそもブラウザでしか動かない
事実として誤り。Firebase の JavaScript SDK は Node.js 上でも動く。正しくは「このアプリの設計上、ブラウザで動かす必要がある」

SDK の制約ではなく、このアプリが何をしたいかから来る要請である。理由は3つ。

  1. signInWithPopup（Google 認証）はブラウザの window を開く処理であり、サーバーには window がない
  2. onAuthStateChanged によるログイン状態の購読は、ブラウザ上で継続的に動き続ける必要がある
  3. ログイン状態の永続化はブラウザの IndexedDB に保存される。サーバーには保存先がない
この区別が重要な理由

「ブラウザでしか動かない」と覚えると、「Firebase を使う以上すべてクライアントコンポーネントにするしかない」 という誤った結論に飛ぶ。実際にはどこで動かすべきかは自分で設計するもの。 9-1 章の AI 機能を実装する段階では「サーバー側で Firebase を扱う」選択肢を検討することになるが、 この誤解を持っていると選択肢自体が見えなくなる。

08

IndexedDB と、認証状態が3つある理由

IndexedDB はブラウザに標準で組み込まれたクライアントサイドのデータベース。 サーバーは一切関与せず、ユーザーのPCの中だけに存在する。

容量 保存できる型 API サーバーへ送信
Cookie 4KB 程度 文字列 同期 毎リクエスト自動送信
localStorage 5MB 程度 文字列のみ 同期（メインスレッドを止める） されない
IndexedDB 数百MB〜 オブジェクト・配列・Blob 非同期 されない

Firebase Auth はログイン時に受け取ったID トークンとリフレッシュトークンをここに保存する。 だからページをリロードしてもログイン状態が消えない。 localStorage ではなく IndexedDB なのは、内部状態をオブジェクトのまま保存でき、非同期で UI をブロックしないため。

実装時に必ず効いてくる：認証状態は3つある

IndexedDB は非同期。つまりページを開いた瞬間、Firebase はまだユーザーがログイン済みか知らない。 トークンを読み出して有効性を確認するまでの数十〜数百ミリ秒、状態は「不明」である。 そのため onAuthStateChanged は最初に必ず null を返しうる。 これを「未ログイン」と解釈すると、リロードのたびに一瞬ログイン画面が表示されてから切り替わるという素人臭い挙動になる。

  1. 確認中（IndexedDB を読んでいる）→ ローディング表示
  2. 未ログイン（確認した結果いなかった）→ ログイン画面
  3. ログイン済み → アプリ本体

仕様書6章で Context に user だけでなくローディング状態を持たせると書いたのは、これが理由。 2状態で作ると必ずバグる。

面接で刺さる論点：トークンの置き場所

IndexedDB は JavaScript から自由に読めるため、XSS を許すとトークンを盗まれる。 対して Cookie には HttpOnly 属性があり、これを付けると JavaScript から一切読めなくなる。 「トークンは HttpOnly Cookie に置くべきか、IndexedDB でよいか」は実務で頻繁に議論される論点であり、 Firebase は SDK の扱いやすさを優先して IndexedDB を選んでいる、というトレードオフの上に成り立っている。

09

npm install は、他人のコードを自分の権限で実行する操作でもある

package.json の scripts には、npm が特定のタイミングで自動実行する予約された名前がある。 dev や build は npm run と打たないと動かないが、 preinstall / install / postinstall は打つ必要がない。 

// node_modules/@firebase/util/package.json
"scripts": {
  "postinstall": "node ./postinstall.js"   ← npm install した瞬間に走る
}
誤解と訂正
npm install はダウンロードする処理ではない
否定ではなく追加。ダウンロードだけではない。またすべてのパッケージがスクリプトを持つわけではなく、今回は439個中3個だけだった

実行されるコードはあなたのユーザー権限で動く。つまりターミナルでできることは何でもできる—— ~/.ssh/id_rsa を読む、.env.local を読む、読んだものを任意のサーバーへ送信する。

規模の問題：4個選んで439個入る

package.json に書いた依存は next / react / react-dom / firebase の4個。 実際に入ったのは 439個。残りは依存の依存として自動的に付いてくる。 

firebase → @firebase/firestore → @grpc/proto-loader → protobufjs

この439個のうち1個でも postinstall に悪意あるコードを仕込まれたら実行される。 しかもその1個の存在すら知らない。攻撃者が狙うのは自分ではなく上流のパッケージで、 メンテナのアカウント乗っ取り・タイポスクワッティング・メンテナ権限の引き継ぎといった手口がある。 event-stream や ua-parser-js で実際に被害が出ている。これをサプライチェーン攻撃と呼ぶ。

npm 11 からこれらはデフォルトでブロックされ、npm warn allow-scripts が出るようになった。 npm 10 以前は警告なしに黙って実行していた。 この防御はごく最近入ったものであり、「npm が止めてくれるから安全」と考えてはいけない。

判断手順（今後も同じことをする）

  1. どのパッケージのどのスクリプトか特定する
  2. node_modules/〇〇/ の該当ファイルを実際に開いて読む
  3. 何をするか確認する（ファイルを書くか / 通信するか / 何もしないか）
  4. 自分のアプリに必要な機能かを判断する
  5. スキップして壊れないか、実際にビルド・lint を回して確認する
今回の判断結果：3つとも承認不要
  • @firebase/util — FIREBASE_WEBAPP_CONFIG が未設定なら何もせず終了する。Firebase App Hosting 用の自動設定機能で、Vercel + .env.local で運用する本アプリには不要。設定されていた場合は apiKey を使って外部通信するので、なおさら動かさない方がよい
  • protobufjs — バージョン表記の警告を出すだけ。ファイルも作らず通信もしない
  • unrs-resolver — ESLint 関連。npm run lint を実際に実行し、問題なく動作することを確認済み
仕様書の判断が、別の角度からも裏付けられた

依存を増やすことは、それ自体がリスクを増やす行為である。 仕様書でカレンダーUIを外部ライブラリなしで自作すると決めたこと、Vite を併用しないと決めたことは、 学習目的だけでなくこの観点からも筋が通っている。

10

package-lock.json は再現性と改竄検知の両方を担う

前提：Vercel は自分の node_modules を見ていない

Vercel がやるのは git リポジトリを clone してビルドすること。 node_modules の439個は .gitignore に入っており git の管理下にすらないので、 Vercel には一切送られない。リポジトリにあるファイルだけを手がかりに、439個を自力で揃え直す。

① 再現性：`^` の曖昧さを消す

"firebase": "^12.17.1" の ^ は「12.17.1 ちょうど」ではなく 「12 系なら新しくてもよい」という範囲指定。 今日は 12.17.1 でも、来月 Vercel がビルドすれば 12.30.0 が入りうる。 lock ファイルは参考情報ではなく命令書で、Vercel が判断する余地をなくす。

怖いのは「必ず壊れる」わけではないこと
  • 今日デプロイしたら動いた。来月、コードを1行も変えずにデプロイしたら壊れた
  • ローカルでは再現しない。自分の node_modules には古いバージョンが残っているから
  • 原因がコードのどこにもない。自分の変更を疑って何時間も溶かす

「何もしていないのに壊れた」——これが再現性のない環境の代償で、実務で最も嫌われる種類の不具合。

② 改竄検知：整合性ハッシュ

lock ファイルには各パッケージの integrity（sha512 ハッシュ）が記録されている。 ダウンロードしたファイルがこれと一致しなければインストールは失敗する。 バージョン番号は同じなのに中身が違う——番号だけでは同一性を保証できないので、ハッシュで中身そのものを照合する。

つまり lock ファイルをコミットしないことは、再現性と改竄検知を同時に捨てることを意味する。 エントリ 09 のサプライチェーンの話と地続きである。

③ npm install と npm ci

npm install は、package.json と lock ファイルが食い違うと lock ファイルの方を書き換えて解決してしまう。本番ビルドでそれが起きると固定した意味がない。

npm install npm ci
lock との不一致 書き換えて解決 エラーで停止
node_modules 差分更新 削除して作り直す
用途 開発中（パッケージ追加時） CI・本番ビルド

Vercel は lock ファイルを検出すると自動的にこの厳密な方式でインストールする。手で打つ必要はない。

ブランチ名とコミットは、未来の自分への索引である

誤解と訂正
git branch -c "start-up-setting" でブランチを作って移動する
git branch -c は --copy＝ブランチの複製であり、移動しない。実行後も main にいるため、そのままコミットすると main に直接入る。正しくは git switch -c chore/firebase-setup

git checkout -b でも同じことができるが、checkout は「ブランチ切り替え」と「ファイル復元」という 無関係な機能を兼ねていて紛らわしい。それを分割するために新設されたのが switch と restore なので、 今から覚えるなら switch を使う。なおブランチ名にクォートもスペースも不要・不可。

命名規約：`種別/内容`

接頭辞用途例
feat/ユーザーに見える機能追加feat/company-list
fix/バグ修正fix/date-format
chore/設定・依存・ビルドまわりchore/firebase-setup
docs/ドキュメントのみdocs/learning-log
refactor/挙動を変えない内部改善refactor/firestore-layer

ルールは小文字・ケバブケース・英語の3つ。 大文字を使わないのは、macOS と Linux でファイルシステムの大文字小文字の扱いが異なり、事故の原因になるため。 （macOS は既定で大文字小文字を区別せず、Linux は区別する。ローカルで通ったものが CI で別物として扱われる。）

却下した案 start-up-setting の問題は2つ。start-up は英語話者にはまず「スタートアップ企業」に見えること、 そして「初期設定」では範囲が広すぎて、create-next-app の話か Firebase の話か ESLint の話か判別できないこと。

1コミット ＝ 1つの目的

取り消せる単位がコミットだからである。 「学習ログの追加をなかったことにしたい」と思ったとき、全部が1コミットなら Firebase の導入ごと巻き戻る。 git revert も git bisect（バグが入ったコミットを二分探索する機能）も機能しなくなる。

コミットメッセージもブランチ名と同じ 種別: 内容 で揃える（Conventional Commits）。 内容は日本語でよいが、接頭辞は英語で統一し、途中で言語を混ぜない。

コミット前に毎回やること

git add の後、コミットする前に git status を実行し、 .env.local が「Changes to be committed」に無いことを目視する。 git add . は使わず、意図したファイルを明示的に指定する。 一度コミットすると、後から消しても git の履歴には永久に残る——秘密情報の誤コミットは取り消せない事故である。

git log もポートフォリオの一部

採用面接でリポジトリを見る人は、コードだけでなくコミット履歴も見る。 フェーズ5まで規約が一貫していれば、git log --oneline --graph そのものが 「計画的に開発した証拠」になる。
